1. Objet et périmètre

HuddleBoard diffuse sur des écrans de production les informations saisies dans un classeur Excel partagé.

Périmètre : HuddleBoard est uniquement la couche d’affichage web. Il ne réalise ni la saisie Excel, ni la publication HTML, ni le transfert Robocopy, ni la gestion des droits Windows, ni la configuration IIS, ThinManager ou RDS.

Environnement connu : Excel et Windows récents côté utilisateurs, Windows Server 2022 avec IIS, ThinManager avec Chrome Container pour certains écrans, sessions RDS pour certains écrans, et éventuellement d’autres appareils web après qualification.

Avant toute intervention, relever dans le ticket les chemins, comptes, groupes, URL, contacts et réglages propres à l’équipe.

2. Comprendre la chaîne des données

Classeur Excel partagé→ Publication HTML Excel→ Robocopy→ IIS→ HuddleBoard→ Terminal / écran

2.1 Classeur partagé

Les membres habilités ouvrent le même fichier Excel depuis le réseau bureautique. Une copie locale ou une pièce jointe ne met pas l’écran de production à jour.

2.2 Publication web

Excel publie un fichier HTML et, selon le classeur, des ressources annexes. La republication est liée à l’enregistrement : la saisie seule ne garantit pas la mise à jour de l’écran.

2.3 Transfert

Le mécanisme d’exploitation utilise Robocopy pour copier la publication vers le dossier web de production correspondant au display. Le détail source/destination, le compte, la fréquence et les journaux doivent être confirmés dans la fiche d’environnement.

2.4 Serveur web

IIS sert l’application et le contenu publié. HuddleBoard charge ce contenu dans une iframe et l’ajuste à l’écran.

2.5 Terminal

Le terminal ouvre l’URL du display affecté à l’équipe via ThinManager / Chrome Container, une session RDS ou un autre navigateur qualifié.

2.6 Disponibilité et fraîcheur

Important : le voyant vert indique qu’une requête HTTP vers le HTML principal a réussi. Il ne prouve pas que la dernière sauvegarde Excel a été publiée et copiée.

La fraîcheur se vérifie aussi avec une valeur métier datée, l’heure d’enregistrement, les fichiers publiés, le journal Robocopy et, si nécessaire, les journaux IIS.

3. Utilisation quotidienne

  1. Ouvrir le classeur partagé depuis le réseau.
  2. Modifier uniquement les cellules prévues.
  3. Enregistrer manuellement avec Ctrl+S ou le bouton Enregistrer.
  4. Attendre le délai communiqué lors de la recette.
  5. Vérifier la valeur attendue sur l’écran.

Le délai réel comprend la publication Excel, l’attente éventuelle du prochain transfert, Robocopy, IIS, le prochain contrôle HuddleBoard et le rechargement du navigateur. La fréquence Robocopy ne constitue pas à elle seule un délai garanti.

En cas d’anomalie, relever avant toute action l’équipe, le terminal, l’heure du dernier Ctrl+S, la valeur attendue, la valeur affichée, le message éventuel et les changements récents.

Ne pas modifier directement la copie HTML de production pour corriger une erreur métier ou masquer une panne en amont.

4. Mise en service d’une nouvelle équipe

Étape 1 — Recueillir la demande

Relever le nom de l’équipe, responsable métier, utilisateurs, écran/terminal, contenu, fréquence attendue, contraintes horaires et contacts IT/exploitation.

Fin : demande et responsabilités identifiées.

Étape 2 — Préparer le dossier réseau

Créer ou identifier le partage du classeur, puis appliquer les droits via les groupes Windows prévus. Tester un compte autorisé et un compte non autorisé.

Fin : accès validés.

Étape 3 — Préparer le classeur Excel

Utiliser le classeur fourni ou le modèle validé. Vérifier qu’il est stocké sur le partage prévu, que les cellules modifiables sont connues et que la configuration de publication survit à une fermeture/réouverture.

Fin : classeur de référence utilisable depuis le réseau.

Étape 4 — Configurer et valider la publication HTML

Configurer Excel vers le répertoire source d’exploitation. Faire deux essais, dont un après fermeture/réouverture. Vérifier le HTML, les ressources annexes et la conservation de la destination.

Fin : l’enregistrement actualise de façon reproductible la publication source.

Étape 5 — Préparer l’identité de transfert

Identifier le compte Robocopy et lui attribuer uniquement les droits nécessaires : lecture source, écriture destination et accès aux journaux requis.

Fin : le transfert fonctionne sous l’identité d’exploitation.

Étape 6 — Configurer Robocopy

Documenter source, destination, compte, fréquence/déclencheur, commande ou script, journaux, comportement de suppression et reprise. Vérifier qu’une modification n’affecte que le dossier cible attendu.

Fin : transfert reproductible et traçable.

Étape 7 — Préparer IIS

Créer ou identifier le répertoire web du display. Vérifier les droits. Depuis le réseau du terminal, tester le HTML et les ressources annexes et vérifier l’absence d’erreurs HTTP.

Fin : contenu accessible sur le chemin web prévu.

Étape 8 — Ajouter le display dans config.js

Le code lit window.AppConfig.displays. Exemple :

window.AppConfig = {
  displays: [{
    name: "Nom affiché",
    slug: "identifiant-url",
    path: "chemin/vers/index.html",
    refreshInterval: 30000,
    description: "Description facultative"
  }]
};

Le code prévoit aussi AppConfig.defaultRefreshInterval. Sans intervalle configuré, la valeur de repli est 30 000 ms.

Fin : l’accueil affiche l’entrée et /display/#/<slug> charge le bon contenu.

Étape 9 — Configurer le terminal

Configurer l’URL du display dans ThinManager / Chrome Container, RDS ou le navigateur qualifié. Vérifier démarrage automatique si requis, plein écran, résolution, absence de dialogue bloquant, accès réseau et certificat éventuel.

Fin : le bon display apparaît sur le terminal réel.

Étape 10 — Recetter de bout en bout

Faire circuler une valeur métier autorisée et relever les heures de saisie, Ctrl+S, publication, transfert, cible IIS et apparition écran. Faire plusieurs mesures. Tester aussi réouverture du classeur, reprise après interruption autorisée, ressource annexe seule et accès non autorisé.

Fin : chaîne validée sur l’écran physique, réserves consignées.

Étape 11 — Documenter l’équipe

Conserver dans le ticket ou référentiel prévu : équipe, classeur, groupe Windows, publication, destination web, slug, URL, terminal/profil, tâche Robocopy, journaux, contacts, date de recette, délai mesuré et réserves.

Étape 12 — Remettre aux utilisateurs

Communiquer emplacement du classeur, règle Ctrl+S, délai observé, support et conduite à tenir. Retirer les données de recette.

5. Recette de la chaîne complète

ContrôleRésultat attendu
AccèsUn membre autorisé ouvre et enregistre ; un compte non autorisé n’accède pas au dossier.
ExcelDeux enregistrements, dont un après réouverture, actualisent le HTML et les ressources.
TransfertLa modification arrive dans le seul dossier visé ; un passage sans changement ne recopie rien d’inutile.
WebHTML et annexes répondent depuis le réseau du terminal.
ÉcranLa bonne équipe apparaît et reste lisible sur l’écran visé.
DélaiPlusieurs mesures fondent la consigne communiquée.
RepriseLes composants concernés retrouvent leur fonctionnement après interruption autorisée.
RemiseManager et utilisateurs disposent des consignes et contacts.
Test obligatoire : modifier uniquement une image ou une ressource annexe. Le moteur actuel compare surtout le texte du HTML principal et peut ne pas recharger l’iframe. Consigner la limite ou la correction retenue.

6. Exploitation et dépannage

Toujours distinguer disponibilité de la page et fraîcheur des données.

  1. Classeur : bon fichier réseau ? enregistrement réussi ? lecture seule ?
  2. Publication : HTML source et ressources mis à jour ? destination conservée après réouverture ?
  3. Transfert : passage Robocopy, identité, code retour et journal corrects ?
  4. IIS : URL directe et annexes accessibles depuis le réseau concerné ? droits et journaux corrects ?
  5. HuddleBoard : slug et path corrects ? console navigateur sans erreur ?
  6. Terminal : profil, URL, session RDS, certificat et cache corrects ?

Comparer les fichiers source et cible en lecture seule avant relance. Ne pas éditer l’export de production pour masquer une panne en amont. Conserver les preuves dans le ticket.

7. Référence technique HuddleBoard

7.1 Fichiers principaux

index.htmlAccueil. Charge config.js et construit une carte par display valide.
config.jsConfiguration des displays.
display/index.htmlLecteur du display : iframe, scaling, refresh et supervision navigateur.
display/displays/Contenus de test/exemple dans la copie du projet ; ne pas les confondre avec la configuration client réelle.

7.2 Sélection du display

L’URL utilise #/<slug>. Le lecteur cherche dans AppConfig.displays l’entrée correspondante.

7.3 Affichage

DisplayManager crée l’iframe, applique le path, initialise la mise à l’échelle et le rafraîchissement. Un chargement dépassant 30 secondes déclenche une tentative de rechargement. Une erreur iframe programme une nouvelle tentative après 5 secondes.

7.4 Mise à l’échelle

ScaleHandler mesure le document de l’iframe, calcule le facteur permettant de contenir tout le contenu dans la fenêtre, applique scale() puis recentre l’iframe. Le mécanisme dépend de l’accès au document iframe et donc des règles same-origin.

7.5 Vérification des changements

RefreshService utilise display.refreshInterval, sinon AppConfig.defaultRefreshInterval, sinon 30 000 ms. Il effectue un GET avec cache: no-cache, ajoute un timestamp à l’URL, abandonne la requête après 10 secondes, lit le HTML en texte, calcule un hash simple et recharge l’iframe lorsque ce hash change après la référence initiale.

Après plus de cinq erreurs consécutives, l’intervalle est doublé jusqu’à un maximum de 300 000 ms.

7.6 Indicateurs et santé

La bannière de statut représente le dernier résultat HTTP pris en compte. La bannière de modification indique l’heure de détection d’un changement. La bannière de santé affiche uptime, refresh et erreurs.

Toutes les 30 secondes, le contrôle de santé est mis à jour. Si performance.memory est disponible et que l’usage dépasse 80 %, des avertissements sont comptabilisés ; après plus de cinq avertissements, la page est rechargée. Un rechargement préventif est aussi programmé toutes les 12 heures.

8. Limites connues de la version fournie

  1. Référence initiale : le premier contrôle établit le hash sans forcer un rechargement.
  2. Ressources annexes : une image modifiée seule peut ne pas déclencher le rechargement.
  3. Ralentissement après erreurs : l’intervalle augmente sans retour explicite à la valeur initiale dans le code fourni.
  4. Timeout : une requête annulée peut laisser le voyant dans son état précédent.
  5. Slug inconnu : aucun message métier spécifique n’est affiché.
  6. Changement de fragment : le code ne réécoute pas explicitement hashchange.
  7. Iframe non isolée : n’accepter que des contenus approuvés par l’entreprise.

9. Sauvegarde et traçabilité

Les sauvegardes doivent couvrir au minimum les classeurs sources, la configuration HuddleBoard, les scripts/tâches de transfert, les paramètres IIS nécessaires, les paramètres ThinManager/RDS et les informations de recette/support.

Le dépôt Git constitue la référence pour le code HuddleBoard. Les anciennes documentations ont été retirées de main afin d’éviter l’usage de procédures non confirmées ; leur historique reste disponible dans Git.

10. Informations propres au site

Les valeurs exactes d’environnement ne sont pas déduites du code. Utiliser A_COMPLETER_ENVIRONNEMENT_CLIENT.txt pour relever serveur IIS, URL, chemins, groupes, comptes, tâche Robocopy, fréquence, journaux, ThinManager, RDS, contacts, sauvegarde et contraintes de maintenance.

Une fois ces informations confirmées, elles peuvent être intégrées à cette documentation et la fiche temporaire supprimée.
